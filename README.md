# Codelab

Образовательная платформа для обучения программированию: LMS-конструктор курсов,
браузерная IDE и автоматическая проверка решений (Judge). Строится по ТЗ
«Техническое задание на разработку образовательной платформы для обучения
программированию v0.1» (19.09.2026).

Разрабатывается как отдельный сервис и интегрируется с существующей LMS
([learning-portal-main](https://github.com/AspWinCode/learning-portal-main),
далее — «портал») через SSO и REST API — см. раздел «Интеграция с порталом» ниже.

## Статус

Это стартовый каркас проекта (v0.1), а не готовая система. Реализовано:

- модель данных из раздела 6 ТЗ (`backend/app/models.py`);
- SSO-вход ученика по одноразовому JWT от портала (IAM-001..003);
- **дерево курса и публикация версий** (LMS-001..006, TASK-001..004): иерархия учебных
  элементов (`POST /courses/{id}/items`, `GET /courses/{id}/tree`), привязка задачи к
  элементу типа task; публикация делает текущий черновик неизменяемым (`published_at`)
  и сразу клонирует его в новый черновик для дальнейшего редактирования — правки после
  публикации не задевают то, что уже назначено ученикам; редактирование опубликованной
  версии запрещено (409); студент видит только опубликованное дерево, методист — черновик;
- отправка и проверка решения по простым тестам stdin/stdout (IDE-004, JDG-001, JDG-004, JDG-005 — частично);
- **изолированный Docker-Runner** (JDG-002, JDG-003, SEC-004): каждый прогон — одноразовый
  контейнер без сети, read-only ФС, с лимитами CPU/RAM/числа процессов, без capabilities,
  от непривилегированного пользователя (`app/services/runner_docker.py`, `backend/sandbox/Dockerfile`);
- **очередь проверки на отдельном воркере** (JDG-001, JDG-012, NFR-005): `POST /submissions`
  только ставит посылку в очередь (`queued`), `python -m app.worker` разбирает её через
  `SELECT ... FOR UPDATE SKIP LOCKED` в Postgres — несколько воркеров не возьмут одну и ту
  же посылку дважды, горизонтальное масштабирование = больше процессов воркера; повтор
  безопасных технических ошибок с backoff, приоритеты (`Submission.priority`), массовая
  перепроверка `POST /courses/{id}/submissions/rerun` (TASK-007, с 2026-09-21 доступна и
  через `/api/lms-admin/...` — методисту, не тренеру, это авторское действие над задачей;
  учитывает только посылки, чьи задачи реально принадлежат курсу). Очередь — таблица в общей Postgres,
  а не отдельный брокер (Redis/RabbitMQ) — проще для MVP, но при очень высокой частоте
  отправок Postgres станет узким местом раньше выделенной очереди;
- зачисление фиксирует точную версию курса на момент выдачи (`Enrollment.course_version_id`,
  MGR-003), прогресс для портала считается по ней же, с разбивкой по курсам;
- **редактор контента, урезанный до Markdown** (раздел 5.3, частично): загрузка файлов
  с allowlist форматов/лимитом размера/безопасным именем (EDT-002/008, SEC-005,
  `POST /api/uploads`), вставка изображения через Ctrl+V и drag-drop (EDT-002),
  автосохранение раз в 15 сек и по blur (EDT-006), предпросмотр как ученик (EDT-007),
  HTML из Markdown санируется DOMPurify на фронтенде перед рендером (SEC-006/007 —
  `marked` иначе пропускает произвольный `<script>` из текста как есть);
- **политика попыток и оценивания** (GRD-001/002/004/005): лимит попыток уже
  проверялся раньше, теперь официальный балл по задаче считается по политике
  курса (лучший/последний/первая принятая попытка — `resolve_official_score`);
  ручная корректировка `PUT /submissions/{id}/grade` с обязательным комментарием,
  исходный авто-результат не перезаписывается; после каждой проверки и после
  ручной оценки пересчитывается `Progress` (раньше эта таблица не заполнялась
  вообще) и доступность зависимых элементов по `unlock_rules` (LMS-004,
  сейчас только форма `{"after_item_id": ...}`) — студенческий `GET /tree`
  возвращает `unlocked` на каждом узле;
- **кабинет ученика** (STU-001/002/004/005): `GET /api/me/dashboard` — активные
  курсы с % прохождения, ближайшие дедлайны, следующий рекомендуемый шаг
  (первая недоделанная обязательная задача), последние результаты по всем
  курсам; `PUT /courses/{id}/last-position` сохраняет последнюю открытую
  позицию (Enrollment.last_item_id) — "Продолжить обучение" на главной.
  Фронтенд: реальное дерево курса вместо текстового поля с id задачи —
  иконки заблокирован/пройден, история попыток при выборе задачи, контент
  нетабличных элементов рендерится как Markdown;
- **аналитика курса для методиста** (ANA-001/002/005): `GET /courses/{id}/analytics` —
  % завершения, средний/медианный балл, число попыток, просроченные зачисления
  (`Enrollment.ends_at`), и по каждой задаче — доля ошибок, среднее число
  попыток до решения, число отказов (зачислен, но не пытался); `generated_at`
  в ответе — дата актуальности метрик;
- **уведомления** (NTF-001/003): внутренние (in-app) — назначение курса, результат
  ручной проверки (обязательные, отключить нельзя) и приближение дедлайна
  (необязательное, `PUT /me/notification-preferences/{type}`); напоминание о
  дедлайне шлётся `app/notify_deadlines.py` — разовый скрипт под внешний cron
  (`0 9 * * * python -m app.notify_deadlines`), не демон, с защитой от повторной
  отправки (`Enrollment.deadline_notified_at`) и пропуском уже завершённых курсов;
- начальная Alembic-миграция (`alembic/versions/25112801a2eb_initial_schema.py`);
- **эксплуатационный статус для администратора** (ADM-004): `GET /admin/status` —
  размер очереди, признак зависшего воркера (самая старая посылка в QUEUED ждёт
  дольше 5 минут — эвристика, не гарантия), системные ошибки за 24ч, занятое/
  свободное место (диск с папкой загрузок). Только `staff_role=admin` — методисту
  и преподавателю, даже с `codelab.manage`, недоступно: это эксплуатационные
  данные, не учебные;
- три интеграционных эндпоинта, которые уже вызывает портал (см. ниже);
- минимальный фронтенд: главная ученика с прогрессом, дерево курса, редактор
  учебного элемента (`/items/{id}/edit`), колокольчик уведомлений.

**Не реализовано и требует отдельного проектирования перед продакшеном:**

- **ADM-001/002/003** (реестр окружений исполнения — версии Python/NumPy/Pandas,
  разрешённые библиотеки как отдельный неизменяемый артефакт) — намеренно не
  делал: это прямо открытый вопрос в самом ТЗ (Q-05), строить реестр вслепую,
  не дожидаясь ответа заказчика, означало бы гадать на выброс;
- **NTF-002** — email/push/мессенджеры как каналы доставки: только in-app;
- GRD-003 (штраф за попытки и просрочку) — ни дедлайна на элементе, ни счётчика
  "платных" попыток сверх бесплатных пока нет;

- ограничение размера вывода на уровне самого контейнера (сейчас обрезаем строку уже
  после того, как `subprocess.run` собрал весь stdout/stderr в память — решение,
  печатающее гигабайты, успеет исчерпать память процесса Judge до обрезки) — JDG-002;
- allowlist разрешённых библиотек и версия окружения как отдельный неизменяемый
  артефакт (ADM-001/002) — сейчас образ один и тот же для всех задач;
- полноценный WYSIWYG вместо Markdown, alt/подпись/размер изображения (EDT-003),
  видео через embed-ссылки с allowlist доменов (EDT-004), подсветка синтаксиса кода
  и рендер LaTeX-формул в предпросмотре (EDT-005), браузерная IDE с автодополнением
  (IDE-001); загруженные файлы раздаются напрямую с диска API-процесса — не через
  объектное хранилище/CDN с подписанными URL, как в целевой архитектуре (раздел 4);
  антивирусная проверка загрузок (SEC-005) не реализована;
- олимпиадный модуль (5.13), античит (5.14) — по ТЗ это Этап 2;
- аналитика (5.11), уведомления (5.12), массовый импорт (IAM-006);
- аудит-журнал с защитой от изменения (OBS-005), мониторинг (раздел 10).

## Архитектура (целевая, по разделу 4 ТЗ)

```
Web app (React) → API gateway/Backend (FastAPI) → LMS service
                                                  → Submission service → Queue → Runner (изолирован) → Checker
                                                  → Object storage (файлы, тесты)
                                                  → Audit/monitoring
```

В этом каркасе Backend API и LMS service объединены в один процесс FastAPI
(`backend/app`); разделение на отдельные сервисы — по мере роста нагрузки
(см. NFR-005 в ТЗ про горизонтальное масштабирование Runner).

## Интеграция с порталом

Три эндпоинта, которые уже вызывает портал (`learning-portal-main/backend/app/services/codelab_sso.py`,
`app/services/kodex_sso.py`) — их контракт менять нельзя без синхронной правки на его стороне:

| Направление | Эндпоинт | Кто вызывает | Назначение |
|---|---|---|---|
| портал → codelab | `GET /api/auth/sso?course={id}&token=...` | редирект ученика из браузера | вход по одноразовому JWT (SSO), автосоздание аккаунта, зачисление на курс |
| портал → codelab | `GET /api/internal/lms-progress/{external_ref}` | сервер портала | отдать прогресс ученика (баллы, курсы, посылки) |
| портал → codelab | `POST /api/admin/courses/{id}/enroll` | сервер портала | зачислить ученика при выдаче доступа в портале |
| портал → codelab | `DELETE /api/admin/courses/{id}/enroll/{external_ref}` | сервер портала | отозвать зачисление |
| codelab → портал | `POST {LMS_BASE}/api/v1/codelab/courses/webhook` | при публикации/снятии курса | обновить пункт витрины курсов в портале |

Все запросы между системами подписываются общим секретом `SSO_KODEX_SHARED_SECRET`
(HMAC-SHA256, заголовок `X-LP-Signature`) — тем же, что уже настроен у портала для
Kodex/ТехноЛаб/PixelForge. JWT из SSO проверяется тем же секретом, `aud` фиксирован
как `"codelab"`.

С 2026-09-19 портал также передаёт в SSO-токене `role`, `groups` и `directions`
ученика (IAM-003) — используйте их для первичного заполнения профиля пользователя,
без отдельного похода в API портала.

### Методист и преподаватель — через аккаунт портала, не напрямую (с 2026-09-21)

Решение: методист создаёт/публикует курсы, а преподаватель просматривает и
оценивает посылки — из своего аккаунта LMS, не заходя в Codelab отдельно (как
уже работает у PixelForge/Kodex). Значит, у Codelab есть **второй, серверный**
API — `/api/lms-admin/*` (`app/routers/lms_admin.py`), вызываемый бэкендом
портала, а не браузером методиста:

| Эндпоинт | Назначение |
|---|---|
| `GET/POST /api/lms-admin/courses` | список курсов / создание |
| `POST /api/lms-admin/courses/{id}/tasks` | создать задачу |
| `POST /api/lms-admin/courses/{id}/items`, `PUT/DELETE /api/lms-admin/items/{id}` | дерево курса |
| `GET /api/lms-admin/courses/{id}/tree` | черновик курса (рабочая версия методиста) |
| `POST /api/lms-admin/courses/{id}/publish`, `.../unpublish` | публикация версии |
| `GET /api/lms-admin/courses/{id}/submissions` | посылки учеников по курсу (TCH-001/003) |
| `PUT /api/lms-admin/courses/{id}/submissions/{sub_id}/grade` | ручная корректировка (GRD-004/TCH-004) |
| `POST /api/lms-admin/courses/{id}/submissions/rerun` | массовая перепроверка (TASK-007) |
| `GET /api/lms-admin/courses/{id}/analytics` | агрегаты курса + рейтинг задач по сложности (ANA-001/002/005) |

Каждый запрос несёт `staff_external_ref`/`staff_full_name`/`staff_role`
(query-параметры) и подпись `X-LP-Signature = HMAC(staff_external_ref, secret)`
— тем же общим секретом, что и остальная интеграция. LMS уже проверила
*permission* пользователя на своей стороне (codelab.manage/codelab.access);
Codelab доверяет подписи и заводит/обновляет лёгкую учётку методиста/
преподавателя лениво — как уже делает `enroll()` для учеников.

С 2026-09-21 добавлена и RBAC-002 (доступ ограничен назначенной областью,
не всей платформой): методист через `staff_role=methodist` видит и может
редактировать/публиковать/смотреть посылки и аналитику **только по курсам,
которые сам создал** (`Course.created_by_id`) — `ensure_course_owner` в
`course_admin.py`, 403 на чужой курс. `staff_role=teacher` видит список
всех опубликованных курсов без ограничения (иначе не из чего выбрать курс
своей группы), но фильтрация посылок по своим группам делается **на
стороне LMS** (`codelab.py` роутер портала) — Codelab групп не знает, LMS
после получения полного списка посылок курса оставляет только учеников из
групп, где текущий пользователь — тренер.

С 2026-09-21 (тем же днём, чуть позже) пробел закрыт: `PUT .../grade` переехал
на `/api/lms-admin/courses/{course_id}/submissions/{submission_id}/grade` —
Codelab сверяет, что посылка правда из заявленного курса (404 иначе), а LMS
теперь может дёшево проверить группу тренера до вызова (списком посылок
курса, который и так уже фильтруется по группе для `GET .../submissions`).

Браузерный вход методиста по SSO-cookie (`/api/courses`, `/api/auth/sso` без
`course`, страница `/items/{id}/edit`) оставлен рабочим как низкоуровневый
путь для локальной отладки Codelab без портала — он использует ту же бизнес-логику
(`app/services/course_admin.py`), но это больше не основной сценарий.

## Запуск для разработки

```bash
cp .env.example .env   # заполнить SSO_KODEX_SHARED_SECRET тем же значением, что у портала
docker compose up -d db
docker build -t codelab-runner:python3.12 backend/sandbox   # образ для изолированного запуска кода
cd backend
python -m venv venv && venv/Scripts/activate  # или source venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --reload --port 8100
python -m app.worker   # отдельным терминалом/процессом — разбирает очередь проверки

cd ../frontend
npm install
npm run dev
```

Если Docker на машине не установлен, для локальной разработки (без проверки
недоверенного кода!) можно временно поставить `RUNNER_BACKEND=subprocess` в `.env` —
код тогда выполняется без всякой изоляции, см. предупреждение в `runner_subprocess.py`.
